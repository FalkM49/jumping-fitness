# Этап 2. Модель данных Firestore и Security Rules

Этот документ — источник правды о структуре данных. Правила лежат в `firestore.rules`,
индексы в `firestore.indexes.json`, Dart-модели в `lib/models/`.
Если меняется схема, меняются все четыре места.

---

## 1. Главные решения

| Решение | Почему |
|---|---|
| **Всё, что влияет на места, тренировки на счету, сроки и роли, пишут только Cloud Functions.** С клиента напрямую возможны всего три записи: профиль при регистрации, заявка в тренеры и токен устройства. | ТЗ 8.1–8.2. Правила блокируют прямую запись, Admin SDK в функциях их обходит. |
| **Тренер тоже меняет календарь и абонементы только через функции.** | Любое действие тренера затрагивает чужие данные: вернуть тренировки всем записанным, отправить push, проверить места. Это нельзя сделать атомарно из приложения. |
| **Роль хранится в `users/{uid}`, а не в custom claims токена.** | ТЗ 2: флаг `isAdmin` ставится вручную в Firebase Console, а Console не умеет ставить claims. При ~20 пользователях лишний `get()` в правилах ничего не стоит. |
| **Расписание по умолчанию виртуальное.** Тренировка по умолчанию (пн/ср/пт) появляется как документ только при первой записи или правке тренером. | ТЗ 3 требует автозаполнения «бесконечно вперёд». Создавать документы на годы вперёд бессмысленно. Приложение само рисует такие ячейки по `settings/defaults`. |
| **Отдельная коллекция `calendar_slots`** хранит, какая тренировка занимает ячейку «день + утро/вечер». | 1) Две активные тренировки в одной ячейке невозможны: функция проверяет слот в транзакции. 2) Отменённая тренировка по умолчанию не «воскресает»: слот запоминает, что день переопределён. 3) Тренер может поставить новую тренировку в слот отменённой, а у записанных клиентов остаётся их запись со статусом «Отменено». |
| **Запись на тренировку лежит в `trainings/{id}/bookings/{uid клиента}`.** | ID документа совпадает с uid клиента, поэтому записаться дважды физически невозможно. Запись, удалённая тренером, остаётся со статусом `removed_by_trainer` и блокирует повторную запись (ТЗ 3.2). |
| **Абонемент: один документ на период.** Текущий помечен `isCurrent: true`, ссылка на него лежит в `users.currentSubscriptionId`. | История сохраняется «как есть» (ТЗ 6). В записи на тренировку хранится, с какого абонемента списана тренировка, чтобы вернуть её туда же. |
| **Дни хранятся строкой `YYYY-MM-DD` по времени студии (Europe/Moscow), моменты — `Timestamp`.** | Календарная сетка оперирует днями, а правило 3 часов и сортировка — точным временем. Строка-день не зависит от часового пояса телефона. |

## 2. Коллекции

Обозначения: `string`, `int`, `bool`, `Timestamp` — типы Firestore.
`day` — строка `YYYY-MM-DD` (день по Москве), `time` — строка `HH:mm`.
**Кто пишет:** 🔒 только Cloud Functions, 👤 сам пользователь (с проверками в правилах).

### 2.1 `users/{uid}` — профиль

| Поле | Тип | Кто пишет | Описание |
|---|---|---|---|
| `fullName` | string | 👤 при регистрации | ФИО, 3–100 символов, без пробелов по краям и управляющих символов (перевод строки, табуляция). В приложении та же проверка — `UserProfile.isValidFullName`. Поиск тренера — по нему (ТЗ 6). |
| `phone` | string | 👤 при регистрации | E.164, например `+79991234567`, — для связи (указывается при регистрации). Правила проверяют формат. Вход — по почте, подтверждённой по ссылке (`email_verified` в токене): без этого правила не пускают никуда. |
| `role` | `'client'` \| `'trainer'` | 👤 только `client`; 🔒 смена | Становится `trainer` после одобрения заявки. |
| `isAdmin` | bool | 👤 только `false`; вручную в Console | Флаг разработчика (ТЗ 2). Админ имеет все права тренера. |
| `createdAt` | Timestamp | 👤 (= время сервера) | |
| `currentSubscriptionId` | string \| null | 🔒 | Ссылка на текущий абонемент. Поля нет, пока абонемента не было ни разу. |
| `monthlyFlower` | `{ month: 'YYYY-MM', flowerId: string }` | 🔒 | Цветок месяца (ТЗ 4). |
| `recentFlowerIds` | string[] (до 2) | 🔒 | Цветки двух предыдущих месяцев, чтобы не повторять цветок три месяца подряд. |

Подколлекция **`users/{uid}/devices/{deviceId}`** хранит токены push-уведомлений (ТЗ 5, этап 7):

| Поле | Тип | Кто пишет |
|---|---|---|
| `token` | string | 👤 |
| `platform` | `'android'` \| `'ios'` | 👤 |
| `updatedAt` | Timestamp (= время сервера) | 👤 |

Токены вынесены в подколлекцию, потому что это единственное, что пользователь меняет сам после регистрации. Сам профиль остаётся полностью закрытым на запись. ID документа — постоянный идентификатор установки приложения. При выходе из аккаунта документ удаляется.

Подколлекция **`users/{uid}/notifications/{id}`** — история уведомлений (этап 7):
`kind`, `title`, `body`, `data` (строки для перехода по тапу), `read`, `createdAt`.
🔒 Создают только функции. Пользователь читает свои и может поменять только `read` на `true`.
Подробнее — в [04_cloud_functions.md](04_cloud_functions.md), раздел «Уведомления».

**Доступ:** свой профиль — себе; все профили — тренерам и админу. Клиенты не видят чужие ФИО и телефоны.

### 2.2 `trainer_requests/{uid}` — заявка в тренеры

ID документа — uid заявителя, поэтому у человека может быть только одна заявка.

| Поле | Тип | Кто пишет | Описание |
|---|---|---|---|
| `uid` | string | 👤 | = ID документа |
| `fullName` | string | 👤 | Обязано совпадать с `users.fullName` |
| `phone` | string | 👤 | Обязан совпадать с `users.phone` |
| `status` | `'pending'` \| `'approved'` \| `'rejected'` | 👤 только `pending`; 🔒 смена | |
| `createdAt` | Timestamp | 👤 (= время сервера) | Дата подачи — показывается админу (ТЗ 2) |
| `decidedAt` | Timestamp | 🔒 | |
| `decidedBy` | string (uid админа) | 🔒 | |
| `adminsNotifiedAt` | Timestamp | 🔒 | Когда администраторам ушло уведомление о заявке — чтобы не повторять |

При регистрации с выбором «Хочу стать тренером» приложение одним batch создаёт профиль (`role: client`) и заявку. Правила это разрешают через `getAfter`.

**Доступ:** своя заявка — себе, список — только админу. Одобрить или отклонить может только функция, которую вызывает админ. Правила такую запись с клиента запрещают.

Подать заявку может только клиент без флага `isAdmin`: у админа и так все права тренера.

Повторная заявка после отказа в v1 не предусмотрена: для неё админ удаляет старый документ в Console.

### 2.3 `settings/defaults` — значения по умолчанию

Один документ, заполняется из `firebase/seed/settings_defaults.json`. Читают все зарегистрированные, пишет только админ через Console.

```ts
{
  timezone: 'Europe/Moscow',
  training: {
    weekdays: [1, 3, 5],        // пн, ср, пт (ISO: 1 = понедельник)
    morningTime: '08:10',
    eveningTime: '18:00',
    durationMinutes: 60,
    capacity: 13,
  },
  subscription: { durationDays: 30, trainings: 11, freezeLimitDays: 3 },
  rules: {
    cancelWindowHours: 3,        // отмена записи строго раньше, чем за 3 ч
    endingSoonDays: 5,           // подсветка и push «скоро закончится»
    lowTrainingsThreshold: 1,    // push «осталась 1 тренировка»
  },
}
```

Если документа нет, приложение и функции берут те же значения из кода (`AppSettings.fallback`).

### 2.4 `calendar_slots/{slotKey}` — кто занимает ячейку

`slotKey` = `YYYY-MM-DD_morning` или `YYYY-MM-DD_evening`.

| Поле | Тип | Описание |
|---|---|---|
| `date` | day | |
| `slot` | `'morning'` \| `'evening'` | |
| `activeTrainingId` | string \| null | Активная тренировка в ячейке, либо `null`, если ячейка пуста |
| `overridesDefault` | bool | `true`, если ячейку трогали вручную. Тогда тренировка по умолчанию здесь больше не рисуется |
| `updatedAt` | Timestamp | |

Как приложение рисует ячейку:

```
если есть документ слота:
    activeTrainingId != null  → показать эту тренировку
    иначе                     → пустая ячейка («+» у тренера)
если документа нет:
    день входит в settings.training.weekdays → виртуальная тренировка по умолчанию, 0/13
    иначе                                    → пустая ячейка
```

Для клиента поверх этого: если в ячейке пусто, а у клиента есть запись со статусом `training_cancelled`, на этот день и слот показывается «Отменено» (ТЗ 3.1). Если тренер поставил в этот слот новую тренировку, показывается она, и на неё можно записаться.

🔒 Пишут только функции, в той же транзакции, что и тренировки.

### 2.5 `trainings/{trainingId}` — тренировка

ID генерируется автоматически.

| Поле | Тип | Описание |
|---|---|---|
| `slotKey` | string | Связь с `calendar_slots` |
| `date` | day | День по Москве |
| `slot` | `'morning'` \| `'evening'` | Строка сетки |
| `startTime` | time | Время начала для отображения |
| `startAt` | Timestamp | Тот же момент абсолютно. По нему проверяется правило 3 часов |
| `durationMinutes` | int | > 0 |
| `capacity` | int | ≥ `bookedCount` (ТЗ 3.2) |
| `bookedCount` | int | Число записей со статусом `active` |
| `status` | `'scheduled'` \| `'cancelled'` | |
| `source` | `'default'` \| `'manual'` | Создана из расписания по умолчанию или тренером |
| `createdAt`, `createdBy` | Timestamp, uid | `createdBy` = `null` для материализованной тренировки по умолчанию |
| `updatedAt`, `updatedBy` | Timestamp, uid | Кто менял последним (ТЗ, этап 2) |
| `cancelledAt`, `cancelledBy` | Timestamp, uid | Только у отменённых |

**Доступ:** читают все зарегистрированные (календарь общий). 🔒 Пишут только функции.

### 2.6 `trainings/{trainingId}/bookings/{clientUid}` — запись на тренировку

| Поле | Тип | Описание |
|---|---|---|
| `clientId` | string | = ID документа. Нужно для запроса «мои записи» |
| `clientName` | string | Копия ФИО для списка у тренера без лишних чтений |
| `trainingId` | string | |
| `trainingStartAt` | Timestamp | Копия `startAt`. Обновляется функцией при переносе тренировки |
| `status` | см. ниже | |
| `subscriptionId` | string | С какого абонемента списана тренировка, туда же её и вернуть |
| `bookedAt` | Timestamp | |
| `cancelledAt` | Timestamp \| null | |

Статусы записи:

| `status` | Когда | Влияние |
|---|---|---|
| `active` | Клиент записан | Занимает место, −1 тренировка |
| `cancelled_by_client` | Клиент отменил раньше чем за 3 часа | +1 тренировка, место освободилось. Можно записаться снова (запись станет `active`) |
| `removed_by_trainer` | Тренер удалил через мусорку | +1 тренировка, место освободилось. **Записаться снова на эту тренировку нельзя** (ТЗ 3.2) |
| `training_cancelled` | Тренер отменил всю тренировку | +1 тренировка. Клиент видит «Отменено» |

**Доступ:** клиент видит только свою запись: отдельный документ или запрос по группе коллекций `bookings` с фильтром `clientId == свой uid`. Тренер видит все записи. 🔒 Пишут только функции.

### 2.7 `subscriptions/{subscriptionId}` — абонемент

Один документ на каждый период абонемента. При продлении старый получает `isCurrent: false` и остаётся в истории без изменений (ТЗ 6).

| Поле | Тип | Описание |
|---|---|---|
| `clientId` | string | Владелец |
| `isCurrent` | bool | У клиента ровно один текущий. Гарантируется транзакцией с `users.currentSubscriptionId` |
| `startDate` | day | «с …» |
| `endDate` | day, включительно | «по …». Сдвигается функцией при заморозке |
| `originalEndDate` | day | Конец до заморозки, для истории |
| `trainingsTotal` | int | Начальное количество, база для шкалы зелёный → красный |
| `trainingsLeft` | int | Текущий остаток, ≥ 0 |
| `freezeLimitDays` | int | Лимит заморозки, задаёт тренер (по умолчанию 3). Если поля нет, приложение берёт значение из `AppSettings.fallback` |
| `freeze` | `{ startDate: day, endDate: day, days: int }` \| null | Использованная заморозка. `null` — заморозка ещё доступна |
| `expiredAt` | Timestamp \| null | Когда плановая функция зафиксировала истечение |
| `burnedTrainings` | int | Сколько тренировок сгорело при истечении (ТЗ 5 п. 3) |
| `notified` | `{ endingSoon: bool, lowTrainings: bool, expired: bool }` | Чтобы push не приходили повторно |
| `createdAt`, `createdBy` | Timestamp, uid тренера | |
| `closedAt` | Timestamp \| null | Когда период стал историей (продление) |

Производные значения приложение вычисляет, а не хранит:

- **Активен** = `isCurrent` и сегодня (по Москве) в `[startDate, endDate]`.
- **Заморожен** = `freeze != null` и сегодня в `[freeze.startDate, freeze.endDate]`.
- **Осталось дней** = `endDate − сегодня + 1`.
- **Можно записаться** = активен, не заморожен, `trainingsLeft > 0` и есть места. Окончательно это проверяет функция (ТЗ 3.1).

**Доступ:** клиент видит только свои абонементы, тренер и админ — все. 🔒 Пишут только функции.

### 2.8 `flowers/{flowerId}` — справочник цветков

Заполняется из `firebase/seed/flowers.json`: 14 цветков из раздела 12 ТЗ, дубль «тёмный пион» удалён.

| Поле | Тип |
|---|---|
| `name` | string |
| `description` | string |
| `meaning` | string — значение на языке цветов |
| `image` | string — путь к ассету в приложении (`assets/flowers/peony.png`), картинки будут на этапе 6 |
| `order` | int |

Читают зарегистрированные, пишет никто: только загрузка сида через Admin SDK или Console.

## 3. Кто что пишет: карта для этапа 4

| Действие (Cloud Function) | Что меняет в одной транзакции |
|---|---|
| `bookTraining(slotKey или trainingId)` | Материализует слот и тренировку по умолчанию, если их ещё нет; `bookings/{uid}` → `active`; `training.bookedCount +1`; `subscription.trainingsLeft −1` |
| `cancelBooking(trainingId)` | Проверка `startAt − now > 3 ч` по серверному времени; запись → `cancelled_by_client`; `bookedCount −1`; `trainingsLeft +1` |
| `createTraining(date, slot, time, duration, capacity)` | Проверка, что `calendar_slots.activeTrainingId == null`; новая тренировка; слот → `activeTrainingId`, `overridesDefault: true` |
| `updateTraining(id, time?, duration?, capacity?)` | `capacity ≥ bookedCount`; при смене времени — новый `startAt` у тренировки и `trainingStartAt` во всех записях; push записанным |
| `removeClientFromTraining(id, clientUid)` | Запись → `removed_by_trainer`; `bookedCount −1`; `trainingsLeft +1`; push клиенту |
| `cancelTraining(id)` | Тренировка → `cancelled`; все активные записи → `training_cancelled` и +1 тренировка каждому; слот → `activeTrainingId: null`, `overridesDefault: true`; push |
| `renewSubscription(clientUid, start, end, trainings, freezeLimit)` | Старый абонемент → `isCurrent: false`, `closedAt`; новый → `isCurrent: true`; `users.currentSubscriptionId` |
| `freezeSubscription(days)` | `freeze == null`, `days ≤ freezeLimitDays`; записать `freeze`; `endDate += days` |
| `approveTrainerRequest(uid)` / `rejectTrainerRequest(uid)` | Вызывающий — админ; заявка → `approved`/`rejected`; при одобрении `users.role = 'trainer'`; push |
| `expireSubscriptionsDaily` (плановая, 00:05 по Москве) | Истёкшие текущие абонементы: `trainingsLeft → 0`, `burnedTrainings`, `expiredAt`, push «истёк». Push «скоро закончится» и «мало тренировок» — этап 7 |
| Плановая, 1-го числа | `monthlyFlower` и `recentFlowerIds` всем пользователям (этап с профилем) |

**Функции реализованы на этапе 4.** Аргументы, проверки, причины отказа и принятые решения
описаны в [04_cloud_functions.md](04_cloud_functions.md). Коротко о решениях:

1. **Куда вернуть тренировку.** В абонемент, с которого её списали, если он ещё текущий;
   иначе в текущий. Если выбранный абонемент уже истёк, возврат учитывается в `burnedTrainings`.
2. **Заморозка** начинается сегодня, `endDate` сдвигается сразу на все дни. В записи
   `freeze` хранятся `startDate`, `endDate`, `days` и `createdAt`. Досрочно выйти нельзя.
3. **Граница слотов** — 14:00. Функции не дают перенести утреннюю тренировку на вечер
   и наоборот. В приложении та же граница: `DaySlot.eveningStartsAt`.
4. **Материализованная тренировка по умолчанию** получает ID `default_{slotKey}`: две
   одновременные первые записи не создадут два документа.
5. **Запись, удалённая тренером**, хранит `removedBy` — uid тренера.

## 4. Индексы

Все индексы описаны в `firestore.indexes.json` и разворачиваются командой `firebase deploy --only firestore:indexes`.

| Запрос | Индекс | Где используется |
|---|---|---|
| `collectionGroup('bookings').where('clientId', '==', uid).orderBy('trainingStartAt')` | составной, группа коллекций: `clientId ↑, trainingStartAt ↑` | Клиент: свои записи на видимый диапазон календаря |
| `collectionGroup('bookings').where('clientId', '==', uid)` | одиночный индекс `clientId` для группы коллекций (fieldOverride) | Запасной вариант без сортировки |
| `subscriptions.where('clientId', '==', uid).orderBy('startDate', desc)` | `clientId ↑, startDate ↓` | История абонементов клиента |
| `subscriptions.where('isCurrent', '==', true).where('endDate', '<', today)` | `isCurrent ↑, endDate ↑` | Ежедневная функция истечения; сортировка «по дням» у тренера |
| `subscriptions.where('isCurrent', '==', true).orderBy('trainingsLeft')` | `isCurrent ↑, trainingsLeft ↑` | Сортировка «по тренировкам» у тренера |

**Список клиентов у тренера (ТЗ 6) сортируется в приложении, а не запросом.** Причин три:

1. Нужно показать и клиентов **без абонемента**, а в запрос по `subscriptions` они не попадут.
2. Вторичная сортировка по ФИО должна идти по русскому алфавиту. Firestore сравнивает строки побайтово, поэтому «Ёлкина» оказалась бы после «Яковлевой».
3. Клиентов около 20: два запроса (`users` с ролью client и текущие абонементы) и сортировка в памяти занимают миллисекунды.

Последние два индекса из таблицы всё равно нужны функциям. Если клиентов станет сотни, те же индексы позволят перенести сортировку в запрос.

Для остальных запросов достаточно автоматических одиночных индексов: календарь по диапазону `date`, слоты по диапазону `date`, `users.where('role', '==', 'client')`.
